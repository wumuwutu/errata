## 1. 产品定位与意义

### 1.1 解决什么问题【定案】

程序员调试时间中有相当一部分是"重复交学费"：一个错误几个月前解决过，再次遇到时已忘记解法，重新搜索半小时。人脑不擅长记错误，机器擅长。

**本产品的意义：把每个错误变成一次性消费——同样的问题，这辈子只交一次学费。**

类比：医院的个人病历。病历不治病，但有了病历，医生不用重新问病史。本工具是程序员的"错误病历本"。

### 1.2 存储的是什么【定案】

存的不只是报错文本，而是一条"错误档案"，四要素：

| 要素 | 内容 | 价值排序 |
|---|---|---|
| ① 错误本身 | 原始 stderr + 归一化指纹 | 原材料 |
| ② 现场 | 触发命令、项目目录、git commit、运行时版本、OS | 上下文 |
| ③ 解法 | 用户记录的修复方法 | **灵魂，最值钱** |
| ④ 时间线 | first_seen / last_seen / 出现次数 / 间隔 | 复盘素材 |

没有③，产品退化为日志文件，毫无意义。因此：**引导用户低成本地写下解法，是产品成败的核心交互；记录报错只是基础设施。**

### 1.3 存储之后能干嘛（价值从小到大）

1. **即时命中**：错误重现 → 自动弹出上次解法（核心价值）。
2. **复盘学习**：`err stats` 展示错误分布（"本月 47% 是依赖/环境问题"），用数据看清自己的技术盲区。
3. **环境迁移**：换电脑/换项目时，`err history --project xxx` 调出该项目历史所有的坑与解法。
4. **周报素材**：`err report` 自动生成"本月解决了 23 个问题……"。
5. **团队模式（二期）**：团队共享错误库，新人踩坑自动获得老人解法，隐性经验组织化沉淀。
6. **远期想象**：脱敏授权的"错误指纹→验证解法"对是稀缺结构化数据，可成为 AI Agent 的记忆层（见 §4.4 MCP 路线）。

### 1.4 适用边界【定案，面试要讲】

- **最适合**：环境、依赖、配置、第三方库、框架类"外部性错误"——最重复、最消耗、最不该重复交学费。
- **不适合**：业务逻辑 bug（自己代码写错）。这类只提供记录入口，不做自动推断。
- 产品文案和面试中要主动声明此边界，这是专业性的体现。

## 2. 核心用户故事（检验意义的标准）

> 三月，配 CUDA 环境，报 `libcudnn.so: cannot open shared object file`，折腾两小时，发现是环境变量指向旧版本。按下 `err fix`，写下："LD_LIBRARY_PATH 被 conda 的 cudnn 污染，删掉 conda 路径即可"。
>
> 七月，换了台服务器，装完环境跑训练——又是这个错。报错刚打出来，终端下方淡出一行字："你 3 月 14 日在 gpu-server-2 遇到过（第 2 次），解法：LD_LIBRARY_PATH 被 conda 污染……"。三十秒解决。

**省下的不只是两小时，是两小时的心智挫耗和心流中断。** 这个共鸣 = 传播力 = GitHub star = 简历上最硬的一行字。

## 3. 形态决策【定案】

**一个本地命令行工具（CLI）+ shell 深度集成。不是 IDE 插件、不是桌面软件、不是 Web 服务。**

理由：
- 报错发生在终端，工具就该长在终端，用户上下文零切换。
- 单二进制分发（Go 编译为一个文件），一条命令安装。参考 fzf / ripgrep / lazygit / starship 的成功路径。
- 不做 IDE 插件的原因：市场红海、审核慢、调试环境复杂。CLI 成功后出插件是顺水推舟（二期）。

技术栈【假设，可议】：
- **Go**（首选）：单二进制、跨平台、生态有 cobra（CLI 框架）、bubbletea（TUI）、creack/pty（伪终端）。
- 备选 Rust：更酷但开发效率低，个人项目节奏优先选 Go。
- 存储：本地 SQLite（含 FTS5 全文检索）。
- Embedding：本地小模型（如 bge-small，几十 MB，首次运行按需下载，不打进二进制）。

产品分层（复杂度递增，按顺序做）：

| 层 | 内容 | 阶段 |
|---|---|---|
| 核心层 | `err` CLI：捕获、指纹、存储、查询、命中提示 | MVP ✅ 已完成 |
| 交互层 | TUI 面板（bubbletea）：历史浏览、筛选、编辑、统计 | 阶段 3 ✅ 已完成 |
| ~~智能层~~ | ~~embedding 语义去重、`err why` LLM 解释、周报~~ | **【已砍·v0.4 修订】** 见 §15：本地模型的配置成本与收益不成正比，保持小而美 |
| 扩展层 | 团队共享、IDE 插件、MCP server | **【推迟】** 当前只做单人模式，视自用反馈再议 |

### 3.1 为什么一期不做 IDE 插件（对"IDE 里点绿三角运行"质疑的回应）【定案】

质疑：很多开发在 IDEA/VS Code 中点按钮运行/调试，错误出现在 IDE 的 Run Console 里，终端 hook 够不着，使用面是否太窄？

回应要点：
1. **按错误类型算，终端是高浓度现场。** IDE 里点按钮报的多是编译错误/断言失败/业务逻辑 bug——本就是工具不覆盖的类型（§1.4）。最重复、最值得记的环境/依赖/配置/部署类错误，几乎全发生在终端或类终端场景（SSH 服务器、CI 日志、docker logs、IDE 内置 terminal）。
2. **IDE 的内置 Terminal 是真 shell。** IDEA/VS Code 的 Terminal 标签页跑的是完整 zsh/bash，shell hook 照常工作。真正捕获不到的只有"点绿三角按钮"这一种触发方式。
3. **架构上为此做好准备：指纹引擎 + 存储必须做成与前端无关的核心库（core library）。** 终端 hook 只是数据源适配器之一；二期 IDEA 插件（监听 ConsoleView 输出流）是另一个适配器，喂同一个引擎、同一个 SQLite 库。插件不是另一个产品，只是多一个输入口。
4. **顺序不能反**：先在终端验证"有人愿意记解法、命中时有价值"，再投入插件的重型开发（Kotlin/Java + IntelliJ API + JetBrains 审核，MVP 周期至少翻倍）。
5. 轻量过渡方案（可选）：`err watch <文件/管道>` 监听日志输出，IDE 的 Run 配置把输出同时写文件即可接入。摩擦高、小众，仅作备选。
6. 参照系：atuin、thefuck 均为纯终端工具，仍获数万 star。终端工具用户"窄但纯"——全是开发者、全在 GitHub、传播和 star 意愿最强。对求职导向项目，这比一个没声响的 IDE 插件价值更高。

## 4. 竞品与差异化（prior art 调研结论）

### 4.1 现有工具对比【定案，已查证】

| 工具 | 做什么 | 与本产品的区别 |
|---|---|---|
| thefuck | 上一条命令打错时自动纠正 | 只修"手滑"，规则匹配，不记忆、不解真实报错。它是"即时纠正"，本产品是"跨时间记忆" |
| atuin | shell 历史命令搜索与同步 | 记"你敲过什么命令"，不感知报错与退出码。本产品记"发生了什么错 + 怎么修的" |
| Fabric / kb 等 | 终端保存笔记片段，可搜索 | 通用剪贴板笔记：手动保存、无指纹、无自动捕获、无命中弹回 |
| howdoi / tldr | 查询某命令怎么写 | 通用知识查询，与个人历史无关 |
| Sentry 等 APM | 线上服务错误监控 | 面向生产环境服务端，不是开发者本地终端体验 |

**结论：自动捕获报错 + 指纹去重 + 关联个人解法 + 重现时自动弹回——这条链路的中间格是空的。**

### 4.2 差异化一句话（README slogan / 电梯陈述）

> "atuin 记得你敲过什么，thefuck 帮你改打错的字，而 err 记得**每个错误是怎么被解决的**——并在它再次出现时把解药递给你。"

### 4.3 真正的三个威胁（诚实面对）

1. **AI 编程工具降维**（Cursor / Claude Code 直接帮修错）：它们解决"这个错怎么修"（通用知识），本产品解决"我上次怎么修的 + 我这个项目/这台机器的特殊性"（个人上下文）。
2. **"我用 Notion 记一下"**：护城河是三个自动化——自动捕获、指纹去重、解决时弹窗。只要摩擦低一个量级，替代不成立。
3. **需求被证伪**：万一用户就是不爱记解法？见 §13 证伪关卡。

### 4.4 进化路线：MCP server

二期提供 `err mcp`，把个人错误库作为记忆层暴露给 AI Agent，从"AI 工具的竞品"变成"AI 工具的基础设施"。这是面试时讲产品演进的好故事。

### 4.5 待做的验证动作（立项第一周）

- [ ] 安装 atuin、thefuck、kb 各用半天，写《相邻方案对比》文档，放入 repo `docs/`。
- [ ] 小调查：问 10–20 个程序员"上一个让你重搜一遍的报错，距上次解决隔了多久？"，记录回答作为需求验证数据。
- [ ] GitHub 搜 error log / terminal history 相关 repo，确认无近三个月新项目抢位。

## 5. 系统架构

```
┌─────────────────────────────────────────────┐
│  捕获层                                       │
│   A. err run <cmd> 命令包装器（PTY 透传）      │
│   B. shell hook（zsh/bash，无感捕获）          │
├─────────────────────────────────────────────┤
│  指纹层                                       │
│   归一化规则 → SimHash 指纹 → embedding 兜底  │
├─────────────────────────────────────────────┤
│  存储层   本地 SQLite（FTS5 全文检索）          │
├─────────────────────────────────────────────┤
│  交互层                                       │
│   命中提示（终端淡色输出）/ TUI / err fix      │
├─────────────────────────────────────────────┤
│  智能层（零件，非主角）                         │
│   解法草稿生成 / err why / 周报                │
└─────────────────────────────────────────────┘
```

### 5.1 捕获层：两种方案

**方案 A：命令包装器（MVP 先做，简单）**

```bash
err run python train.py
```

原理：子进程执行命令，透传 stdin/stdout/stderr。**必须用伪终端（PTY）转发**（Go 用 creack/pty），否则交互式命令（vim/top）和带颜色输出会坏。退出码 ≠ 0 时记录 stderr 全文。

铁律：**stderr 原样透传给用户，只做旁路录制，绝不拦截、绝不延迟**。用户感知不到你的存在。

**方案 B：shell hook（核心卖点，无感，阶段 3 做）**

- bash：DEBUG trap + PROMPT_COMMAND；zsh：preexec / precmd 钩子。
- 每条命令前记录命令文本与时间戳；命令后读 `$?`，非零且 stderr 非空时触发记录。
- stderr 捕获：mkfifo + 后台 disown 的 tee 读 fifo，shell `exec 2> fifo`——原样显示 + 落一份到缓冲区。后台任务在 job control 下有独立进程组，Ctrl-C 的 SIGINT 群发打不到 tee（早期 `2> >(tee …)` 进程替换形态与 shell 同前台进程组，Ctrl-C 会打死 tee，SIGPIPE 连锁杀掉 bash 5.2 的 shell 本身，v0.1.14 CI 实测暴露）。
- 安装方式：用户 `.zshrc` 加一行 `eval "$(err init zsh)"`（direnv/starship 同款标准做法）。

**不选方案 C（eBPF/全局进程监控）**：跨平台地狱、权限要求高，过度工程。

### 5.2 数据模型（SQLite）

```sql
CREATE TABLE errors (
  id INTEGER PRIMARY KEY,
  fingerprint TEXT UNIQUE,      -- SimHash 指纹 hex
  signature TEXT,               -- 归一化后的错误签名
  raw_sample TEXT,              -- 一条原始 stderr 样本
  language TEXT,                -- python / node / java / unknown
  project_dir TEXT,
  created_at TIMESTAMP,
  first_seen TIMESTAMP,
  last_seen TIMESTAMP,
  count INTEGER DEFAULT 1
);

CREATE TABLE fixes (
  id INTEGER PRIMARY KEY,
  error_id INTEGER REFERENCES errors(id),
  solution TEXT,                -- 用户确认后的解法
  draft TEXT,                   -- 系统生成的草稿（保留追溯）
  commands_between TEXT,        -- 报错到解决之间的命令序列（JSON）
  git_diff_ref TEXT,            -- diff 摘要引用
  created_at TIMESTAMP
);

CREATE TABLE pending (          -- 未决错误（无解法）
  id INTEGER PRIMARY KEY,
  error_id INTEGER REFERENCES errors(id),
  detected_at TIMESTAMP,
  status TEXT                   -- pending / resolved / skipped / archived
);
-- FTS5 虚拟表对 signature + solution 建全文索引
```

## 6. 错误指纹算法（技术核心，面试深挖点）【定案方向，参数可调】

目标：同一错误，路径/行号/PID/时间戳变化 → 指纹相同；不同错误即使相似 → 指纹不同。

### 6.1 归一化管线

```
原始 stderr
 → 1. 剥离 ANSI 颜色码
 → 2. 归一化替换（按优先级）：
      绝对路径 /Users/xxx/…  → <PATH>
      十六进制地址 0x7f…     → <ADDR>
      行号 line 42 / 数字    → <N>
      UUID / 时间戳 / IP     → <UUID> / <TS> / <IP>
      引号内变量值           → <VAL>
 → 3. 提取错误签名：最后一帧异常类型 + 消息模板
      例：TypeError: unsupported operand <VAL>
 → 4. SimHash / MinHash → 64 位指纹
```

### 6.2 两层匹配架构

| 层 | 机制 | 职责 |
|---|---|---|
| 第一层：精确+模糊哈希 | 指纹完全相同 → 直接命中；海明距离 ≤ 阈值（初始 6，实验定）→ "相似错误" | 快、可解释 |
| ~~第二层：embedding 语义兜底~~ | ~~本地小模型对错误签名取向量，余弦相似度 > 0.92 判同错~~ | **【已砍·v0.4】** 单层 SimHash 为定案，见 §15 |

~~**两层架构是面试亮点：确定性系统 + 概率系统，各处理对方盲区。**~~（v0.4：该叙事随智能层一并放弃）

### 6.3 阈值原则【定案】

**宁可漏报，不可错报。** 错报（把不同错误认成同一个）会给出错误解法、摧毁信任；漏报只是退回现状。调阈值时永远偏向精确率（precision）。

### 6.4 评测集（阶段 2 的核心交付物）

- 收集 300–500 条真实报错语料（自己的终端 history、公开 issue、同学贡献），人工标注"哪些是同错"。
- 实验项：不同归一化规则组合 × 不同海明阈值 → precision/recall 曲线，定阈值。
- 消融对比：纯正则 vs 纯 embedding vs 两层架构。
- 产出技术博客：《给报错做指纹：确定性规则与语义模型的分工》——**简历核心弹药**。

### 6.5 语言支持范围【定案：MVP 克制】

MVP 只做 **Python + Node** 两种报错的归一化；阶段 2 加 Java。三家的 traceback 格式吃透，胜过十种语言半吊子。README 明确写不支持清单。

## 7. 解法捕获：状态机设计（产品成败核心）【定案】

### 7.1 诚实前提

**软件不可能自动知道解法。** 真正的设计目标：把"人告诉它解法"的摩擦降到接近零，并在人不说时尽量自动猜出线索。

关键洞察：用户解决报错的一瞬间情绪最高（"终于搞定了！"），**此刻记录意愿最强、记忆最鲜活**。错过此刻让他回头补录，永远不会发生。所以：不报不录，解决后立刻拦一下。

### 7.2 状态机

```
                    报错发生（stderr捕获+指纹）
                           │
                           ▼
                     ┌──────────┐
                     │ PENDING  │  静默等待，完全不打扰
                     └──────────┘
                           │
          ┌────────────────┼────────────────────┐
          │ 5分钟内同目录    │ 超时/N天            │ 用户主动
          │ 有命令成功(退出0) │ 无成功信号          │ err fix
          ▼                ▼                    ▼
   ┌────────────┐   ┌───────────┐        ┌────────────┐
   │ DETECTED   │   │ ARCHIVED  │        │ PROMPTED   │
   │ _SUCCESS   │   │ (不删,不   │        │            │
   └────────────┘   │  计入统计) │        └────────────┘
          │         └───────────┘              │
          ▼                                    │
   生成解法草稿（§7.3）                          │
          │                                    │
          ▼                                    ▼
   ┌─────────────────────────────────────────────┐
   │ 终端轻提示:                                    │
   │ "刚才的 TypeError 好像解决了？回车记录(10s)Esc跳过"│
   └─────────────────────────────────────────────┘
          │              │              │
        用户确认        用户编辑        用户跳过
          │              │              │
          ▼              ▼              ▼
      RESOLVED       RESOLVED       SKIPPED
      (草稿入库)     (修改后入库)   (保留pending,
                                    下次可 err pending 补录)
```

### 7.3 解法草稿自动生成（人从"写作"降级为"审阅"）

| 信号源 | 机制 | 可信度 |
|---|---|---|
| 命令历史推断 | 报错到解决之间的命令序列；若解法是单条命令（如 pip install torch）→ 直接预填 | 高 |
| git diff 快照 | 报错时存 diff hash 引用，解决时再 diff，提取变更摘要 | 中 |
| LLM 压缩 | 把命令序列+diff 摘要压成一句自然语言草稿 | 辅助 |

**铁律：草稿只是预填，落库前必须经人确认。** 自动猜的解法直接入库会污染数据、摧毁信任。

### 7.4 自动推断的边界（诚实划分）

| 解法类型 | 能否自动推断 | 原因 |
|---|---|---|
| 装包/改环境变量/重启服务 | 高准确率 | 解法就在命令序列里 |
| 改配置文件某项 | 可推断 + LLM 草稿 | diff 有信号，语义需人确认 |
| "我逻辑写错了" | **永远不行** | 理解代码意图需要人脑 |

### 7.5 防"尸体数据"（无解法的 pending 堆积）

- `err pending` 列出所有未决错误，支持批量快速补录。
- 未决超过 N 天自动归档（不删，不计入统计）。
- **核心健康指标埋点：记录率 = 有解法错误数 / 总错误数。低于 40% 说明交互摩擦太大，回去改设计，而不是怪用户懒。**

### 7.6 命中时的展示规范【定案：克制】

```
── err ── 你于 2025-11-03 在 ~/projects/api 遇到过此错误（第3次）
   解法：pip 装的版本和 conda 环境冲突，执行 conda deactivate 后重装
   [err show 3 查看详情 | err edit 更新解法]
```

- 默认灰色、两行以内、可配置关闭。
- **绝不喧宾夺主——打扰用户一次，用户就卸载。**

## 9. 硬性红线【定案，不可妥协】

1. **性能红线**：shell hook 在每条命令的返回路径上，注入代码必须 < 50ms。指纹计算必须极快；embedding 异步做（先正则判，embedding 后台补判）。
2. **隐私红线**：本地优先，永不上传（远期数据飞轮需显式 opt-in 授权 + 脱敏）。报错可能含密码/token/内网地址：提供敏感信息脱敏规则 + `err ignore` 黑名单 + README 第一行明示。
3. **透传红线**：stderr 原样透传，旁路录制，绝不拦截或延迟用户命令。
4. **阈值红线**：宁可漏报不可错报，偏向 precision。
5. **卸载红线**：`err uninstall` 清理 shell 配置与数据目录——精致感体现在退场。
6. **克制红线**：命中提示 ≤ 2 行、灰色、可关闭。

## 16. 分发、安装与更新机制

### 16.1 发布在哪【定案】

**GitHub 是唯一主阵地**：开源（MIT）+ Releases 发布预编译二进制。开发者工具的发现的信任链 = GitHub star + README + 社区帖子（Show HN / V2EX / 掘金 / Reddit r/commandline），不需要应用商店。

### 16.2 用户怎么安装（按优先级，全部支持）

| 渠道 | 用户命令 | 说明 |
|---|---|---|
| ① 一键脚本（首发主力） | `curl -fsSL https://xxx/install.sh \| sh` | 行业标准做法（starship/atuin/rustup 同款）。脚本检测 OS/架构 → 从 GitHub Releases 拉对应二进制 → 放到 `/usr/local/bin` 或 `~/.local/bin` → 校验 SHA256 → 提示执行 `err init`。脚本本身开源放在 repo 里，透明可审计（用户对 curl\|sh 有安全顾虑，脚本可读是信任前提） |
| ② Homebrew（macOS/Linux，最体面） | `brew install <你>/tap/err` | 自建 tap 仓库（一个 GitHub repo 放 formula），发布时 CI 自动更新 formula。star 数过千后可申请进 homebrew-core |
| ③ 包管理器长尾 | `go install`、`cargo binstall`（如换 Rust）、`scoop`（Windows）、AUR（Arch） | 有社区用户会主动帮你维护 AUR，前期自己只做 go install |
| ④ 手动下载 | GitHub Releases 页面直接下载二进制 | 兜底，面向受限环境 |

**回答"命令行直接下载吗？"：是的，全程命令行，无任何图形安装器。** 这正是目标用户期待的方式。

### 16.3 怎么发布一个新版本（自己的流水线）

- 用 **GoReleaser + GitHub Actions**：打 tag `v0.2.0` → CI 自动交叉编译（macOS amd64/arm64、Linux amd64/arm64、Windows）→ 生成 checksums → 上传到 GitHub Releases → 自动更新 Homebrew tap formula。
- 配好一次，以后发版 = 打一个 tag，零手工。这条流水线本身也是简历亮点（"完整的开源发布工程化"）。
- 版本号遵守语义化版本（SemVer）；每个 Release 写清楚的 CHANGELOG（新增/修复/破坏性变更）。

### 16.4 用户怎么获得更新（三层机制）

| 机制 | 说明 | 阶段 |
|---|---|---|
| ① 包管理器升级（主力） | `brew upgrade err` 等，用户用各自包管理器的原生升级方式 | 首发即支持 |
| ② 更新提示（体验关键） | CLI 启动时**异步、最多每天一次**检查 GitHub Releases 最新版本，有新版时在命令输出末尾淡色提示一行："err v0.2.0 已发布，brew upgrade err 更新"。铁律：**异步执行、不阻塞命令、可配置关闭、绝不自动下载替换**（呼应 §9 性能与克制红线） | 阶段 4 |
| ③ `err update` 自更新命令 | 非包管理器安装的用户可一条命令拉最新二进制自替换（校验签名/SHA256） | 可选，二期 |

### 16.5 注意事项

- **版本检查要节流**：本地存 last_check 时间戳，24 小时内不重复请求；离线/超时静默跳过，绝不能因 GitHub 访问失败影响正常功能（国内网络环境尤其重要，可考虑镜像或仅在交互命令时检查）。
- **数据库迁移**：SQLite schema 会随版本演进，用 migration 机制（如 goose 或自写版本号表），用户升级后旧数据必须无损迁移——丢用户解法数据是致命事故。
- **不要内置强制自动更新**：开发者工具用户厌恶软件在后台偷偷换二进制；提示 + 用户主动升级是社区惯例。
- 安装脚本和 `err init` 要明确告诉用户改了什么文件（如 `.zshrc` 加了一行），卸载时精准回滚（呼应 §9 卸载红线）。

## 17. 技术栈与开发环境

### 17.1 技术栈【主语言定案 Go，依赖库可议】

| 用途 | 选型 | 备注 |
|---|---|---|
| 主语言 | Go 1.22+ | 单二进制、跨平台编译、CLI 生态最成熟（fzf/lazygit 同款） |
| CLI 框架 | cobra + viper | 子命令 + 配置，Go CLI 事实标准 |
| TUI | bubbletea + lipgloss | 精致感主要来源（charmbracelet，lazygit 同款审美） |
| 伪终端 | creack/pty | PTY 透传核心依赖 |
| 数据库 | modernc.org/sqlite（纯 Go 实现） | **关键选择**：避开 CGO，交叉编译无障碍；勿用 mattn/go-sqlite3 |
| SimHash | 自实现（约 100 行） | 算法简单，自己写是面试资产，不引库 |
| Embedding | ONNX Runtime Go 绑定 或 HTTP 调本地 ollama | 【假设】阶段 4 再定 |
| 发布 | GoReleaser + GitHub Actions | 见 §16.3 |

### 17.2 开发环境【定案：必须在类 Unix 环境开发】

核心约束：工具运行在 macOS/Linux 的 zsh/bash 里，Windows 裸机无法开发调试。

- **Mac 主力机**：最理想，原生开发，iTerm2 + zsh 即测试现场。
- **Windows 主力机（最常见）**：装 WSL2（Ubuntu），全部开发在 WSL2 内进行，VS Code 装 WSL 插件远程接入。macOS 兼容性初期靠 GitHub Actions macOS runner 自动化测试兜底，发布前找真实 Mac 实测。**Windows 原生（cmd/PowerShell）支持放最后，v1.0 可不支持**——WSL2 才是开发者报错的主战场。
- **Linux 主力机**：直接开发，同样需 Mac 测试途径。

### 17.3 环境清单

必装：Go 1.22+、Git + GitHub CLI（gh）、VS Code（gopls）或 GoLand、zsh + bash 双 shell、Docker、golangci-lint（与 CI 同款检查）。

测试矩阵（差异化质量来源）：
- bash 5.x（主测）、**bash 3.2（macOS 自带的古老版本，行为差异大，CI 覆盖）**、zsh 5.x（主测）、fish（明确不支持，但要测"优雅拒绝"）。

### 17.4 两条关键实践

1. **Dogfooding 从第一天开始**：MVP 能跑起，开发本项目的所有终端操作就走 err 捕获。开发过程自产大量真实报错 = 最现成语料库 + 试用场景（§13 自用黏性关卡依赖此）。
2. **CI 第一天就配**：GitHub Actions 矩阵 os: [ubuntu, macos] × shell: [bash, zsh]，每次提交四组合跑测试。shell 兼容性 bug 靠人肉测不过来。
